# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Stack

- **PHP 8.3** — undefined constants are fatal `Error`, not warnings (critical for any constant usage)
- **MariaDB** (latest) via `MYSQLi_DB` class
- **Apache** inside Docker — no build step, no transpilation, files are served directly

## Docker Environment

```bash
# Start all containers (web :8084, phpMyAdmin :8085, MariaDB :3309)
docker compose up -d

# Tail PHP/Apache errors
docker exec travian-need-fix-web tail -f /var/log/apache2/error.log

# Run a PHP script inside the container (for quick DB tests)
docker exec -w /var/www/html/GameEngine travian-need-fix-web php yourscript.php

# MySQL shell
docker exec travian-need-fix-db mariadb -uroot -prootpassword travian
```

Game URL: `http://localhost:8084`  
Test credentials: `TESTUSER / 123456`

`GameEngine/config.php` is **git-ignored** (generated by the installer). It holds all live constants (`SQL_*`, `TB_PREFIX`, `DOMAIN`, `SPEED`, `WORLD_MAX`, `START_DATE`, etc.). Never commit it.

## Architecture

### Request lifecycle

Every game page (e.g. `dorf2.php`) follows this pattern:

1. `GameEngine/Generator.php` → included first, creates `$generator` global
2. `GameEngine/config.php` → all constants loaded (`TB_PREFIX`, `SPEED`, etc.)
3. `Security/Security.class.php` → request filtering
4. `GameEngine/Database.php` → instantiates `$database` (class `MYSQLi_DB`) and all service globals (`$units`, `$battle`, `$technology`, `$ranking`) at file scope via self-instantiation at the bottom of each class file
5. `GameEngine/Lang/{LANG}.php` → all UI string constants
6. `GameEngine/Village.php` → builds `$village` (current player's village state)
7. `GameEngine/Automation.php` → **runs the full game cron tick on every page load** (protected by `automation.lck` — stale after 60s)
8. `Templates/*.tpl` — PHP-in-HTML view files, included directly

### Build queue (`bdata` table)

Columns: `id, wid, field, type, loopcon, timestamp, master, level`

- `loopcon=0` → **active** job (counts against the concurrent build limit)
- `loopcon=1` → **queued** (Travian Plus waiting loop); `timestamp` stores `activeFinishTime + ownDuration`, always in the future — **never** compared against `now` for completion
- `master=1` → pending **Master Builder** job (not yet activated; activated by `MasterBuilder()` in Automation when resources are available, which sets `master=0`)

Build queue functions in `Database.php`:
- `getBuildingByField($wid, $field)` → non-master jobs for a field (active + loopcon)
- `getMasterJobsByField($wid, $field)` → master=1 jobs for a field
- `getJobs($wid)` → all jobs ordered by `master, timestamp ASC`

`buildComplete()` in `Automation.php` processes jobs where `timestamp <= now AND master=0`. After completing an active job, it promotes exactly one `loopcon=1` job to `loopcon=0` (the one with the lowest timestamp for that village/condition), then deletes the completed record.

Level-number display in templates: `currentLevel + 1 + count(getBuildingByField) + count(getMasterJobsByField)` — both functions never overlap (a promoted master job becomes `master=0`).

### Automation tick

`Automation::__construct()` runs the tick. The method list in `$methodsArrays` (around line 86) is iterated with a per-file lock in `GameEngine/Prevention/`. Each method is wrapped in `try/catch(\Throwable)` — a failure in one method logs via `error_log` and continues with the next.

Key automation methods and their guard conditions:

| Method | Trigger |
|---|---|
| `buildComplete` | `bdata.timestamp <= now AND master=0` |
| `spawnNatars` | day ≥ `NATARS_SPAWN_TIME`, artifacts not yet spawned |
| `spawnWWVillages` | day ≥ `NATARS_WW_SPAWN_TIME`, WW villages not yet spawned |
| `spawnWWBuildingPlans` | day ≥ `NATARS_WW_BUILDING_PLAN_SPAWN_TIME`, plans not yet spawned |
| `buildNatarWW` | day ≥ `NATARS_WW_SPAWN_TIME`, interval since last upgrade ≥ `NATARS_WW_BUILD_INTERVAL` |
| `MasterBuilder` | runs outside the locked loop; activates pending `master=1` jobs when resources available |

### Natars NPC

- **Natars uid = 3**, tribe = 5. `uid=5` is the Multihunter admin account.
- Always reference as `Artifacts::NATARS_UID` (a class constant). There is **no global `NATARS_UID` constant** — using a bare `NATARS_UID` is a fatal error in PHP 8.3.
- `NATARS_WW_BUILD_INTERVAL` in `config.php` is computed as `86400 / SPEED` so the NPC can complete a WW in a reasonable real-world time on fast servers.

### Template system

Templates live in `Templates/`. They are plain PHP-in-HTML files included by game pages. Build-related UI is in `Templates/Build/`:
- `upgrade.tpl` / `wwupgrade.tpl` — upgrading an existing building
- `next.tpl` — plus-queue slot display
- `avaliable/availupgrade.tpl` — new construction slot
- Individual building templates are numbered by building type ID (`16.tpl` = Marketplace, `40.tpl` is the WW, etc.)

### Static game data

`GameEngine/Data/buidata.php` — global arrays `$bid1` through `$bid40`+. Each index is a building type; each sub-array index is the level. Keys: `wood`, `clay`, `iron`, `crop`, `pop`, `cp`, `time`, `attri`, `prod`. These are accessed throughout the engine as `$GLOBALS["bid".$type][$level]`.

### Language / i18n

Primary language file: `GameEngine/Lang/en.php` (~1800 lines of `define()` calls).
Arabic is split into parts: `GameEngine/Lang/ar/part1.php` through `part5.php` (loaded by `GameEngine/Lang/ar.php`).
Language is selected by `LANG` constant in `config.php`. All UI strings are constants.

## Database

Table prefix is `TB_PREFIX` (e.g. `s9099_`). Always use `TB_PREFIX` in queries, never hardcode a prefix.

Key tables:
- `{prefix}users` — player accounts (uid 1–5 are system accounts: Support, Nature, Natars, Taskmaster, Multihunter)
- `{prefix}vdata` — villages (`natar=1` means WW village)
- `{prefix}fdata` — village resource/building state (`f1`–`f18` = resource fields, `f19`–`f40` = building slots, `f{n}t` = building type at slot n, `f99` = WW level)
- `{prefix}wdata` — world map tiles (`occupied`, `fieldtype`, `x`, `y`)
- `{prefix}bdata` — build queue (see above)
- `{prefix}artefacts` — artifact ownership (`type=15` = WW building plans)

`MYSQLi_DB` has an in-memory cache for `bdata` per village. Any function that writes `bdata` should invalidate it or use `use_cache=false`. `$database->query_return($q)` returns an array of associative rows; `$database->query($q)` returns the raw mysqli result.

## Configuration knobs (config.php)

| Constant | Effect |
|---|---|
| `SPEED` | Server speed multiplier; affects build times, production, `NATARS_WW_BUILD_INTERVAL` |
| `START_DATE` | `dd.mm.yyyy` — used to calculate when each Natars phase triggers |
| `NATARS_SPAWN_TIME` | Days after `START_DATE` to spawn Natars + artifacts |
| `NATARS_WW_SPAWN_TIME` | Days after `START_DATE` to spawn WW villages |
| `NATARS_WW_BUILDING_PLAN_SPAWN_TIME` | Days after `START_DATE` to spawn building plans |
| `NATARS_WW_BUILD_INTERVAL` | Seconds between Natars auto WW upgrades (auto-scaled by SPEED) |
| `WORLD_MAX` | Map radius; affects `generateBase` radius calculations |
| `ALLOW_ALL_TRIBE` | If true, all tribes get the Roman dual-queue benefit |
| `TB_PREFIX` | Database table prefix |

## Testing approach

There is no test suite. To verify changes safely:
1. Write a PHP script in `GameEngine/` starting with `define('AUTOMATION_MANUAL_RUN', true);` then `include_once('Database.php');` — this bootstraps all globals.
2. Instantiate with `new MYSQLi_DB(SQL_SERVER, SQL_USER, SQL_PASS, SQL_DB, SQL_PORT)`.
3. Use `mysqli_query($database->dblink, "START TRANSACTION")` / `ROLLBACK` for any write tests.
4. Run inside the container: `docker exec -w /var/www/html/GameEngine travian-need-fix-web php yourscript.php`
5. Delete the script when done.

To trigger automation manually: `new Automation();` after the bootstrap (the `AUTOMATION_MANUAL_RUN` define skips the lock-file gate).
